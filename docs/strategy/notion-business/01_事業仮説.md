# 01_事業仮説

## 事業仮説の要約

Proof Gateは、汎用AI品質保証SaaSとして広く売るよりも、まずRAG/AIチャットボット導入会社向けに「納品品質レポート」と「重大誤回答チェック」を提供する方が受注理由が明確で、学習速度も速い。

## なぜ汎用AI品質保証SaaSから始めないのか

- 汎用SaaSだと導入理由が曖昧になりやすい
- 品質保証の必要性は理解されても、今すぐの予算化理由が弱い
- 初期顧客は機能比較よりも「この案件で何が判断できるか」を求める
- 現段階ではマルチテナント、認証、課金、運用UIよりも、レポートと検査プロセスの再現性が重要
- 案件を通じて失敗パターン、重大度分類、業界別観点を集めた方が資産化しやすい

## なぜRAGベンダー / AI導入会社向けから始めるのか

- PoC後に顧客へ品質を説明しにくいという痛みが強い
- 本番移行の稟議材料を作る必要がある
- 納品後の誤回答責任を下げたいニーズがある
- 保守運用メニューに変更時チェックを組み込みやすい
- 1社に刺さると複数案件へ横展開しやすい

## どの購買理由を狙うのか

| 購買理由 | 具体的な状況 | 提案する価値 |
|---|---|---|
| 本番移行の判断材料がほしい | PoCは終わったが品質説明が弱い | 顧客提出用の納品品質レポート |
| 誤回答リスクを減らしたい | 返金・解約・規約説明の誤回答が怖い | 重大誤回答チェックとS1/S2分類 |
| 顧客への説明力を上げたい | 提案で差別化しにくい | レポート添付型の営業導線 |
| 保守運用を月額化したい | 納品後の接点が続かない | FAQ/規約変更後チェックと継続Monitor |
| 既存RAGの改善優先度を知りたい | 問題はあるが何から直すべきか不明 | 失敗パターン別の改善優先度整理 |

## 診断 → レポート → 継続Monitor → 第三者検査の進化仮説

### Phase 1: 診断

- 個別案件に対し、重大誤回答があるかを確認する
- 返金、解約、料金、規約、例外条件などの高リスク論点に絞る
- 「直すべき問題があるか」を見つける入口商品にする

### Phase 2: レポート

- 診断結果を顧客提出できる納品品質レポートに変換する
- PoC後に何を判断できるかを明文化する
- 営業資料ではなく、顧客説明・社内稟議・本番判断に使う資料にする

### Phase 3: 継続Monitor

- FAQや規約変更後の再チェックを定例化する
- ベンダー保守メニューやエンド企業の月次運用に載せる
- 単発診断ではなく、変更管理の一部にする

### Phase 4: 第三者検査

- 「自社評価」ではなく「外付け第三者検査」として位置づける
- 業界別Gate Policy、重大誤回答パターン、レポート型を標準化する
- 将来的に、監査・受入判定・ベンダー比較に使える水準へ近づける

## 初期の勝ち筋仮説

- まずはベンダー案件で1件有償PoCを取る
- そのPoCをもとに、顧客提出レポートの型を磨く
- 同時にFAQ/規約変更後チェックを継続商品として提案する
- ベンダー経由で複数案件に入り、失敗パターンを資産化する

## 現時点での前提

- 参入障壁はまだ弱い
- 勝ち筋はプロダクト機能の多さではなく、実案件で使えるレポートと運用導線
- 有償PoCと継続Monitorを通じて、徐々に共通資産を積み上げる
